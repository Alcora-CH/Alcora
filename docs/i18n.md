# Languages (i18n)

Alcora ships in **French, English, German and Italian**. This document is written in
English on purpose: it is the one file a translator or a fork needs, and English is the
contributors' language of this project (so is the diagnostic log — see below).

The architecture has **no i18n library**. It is two flat dictionaries per language, a
tiny store, and two contracts that make an incomplete translation fail the build. If you
keep the contracts green, you cannot ship a half-translated language by accident.

## Where everything lives

| Piece | Path | Enforced by |
|---|---|---|
| UI dictionaries (per language) | `v2/web/src/i18n/fr.ts`, `en.ts`, `de.ts`, `it.ts` | TypeScript: each file is `Record<Cle, string>` |
| UI registry (language list, locales, names) | `v2/web/src/i18n/index.ts` → `LANGUES` | — |
| Shared subject/vehicle names | `v2/web/src/i18n/sujets.ts` | same dictionaries |
| Main-process dictionaries + registry | `v2/desktop/i18n.js` → `FR/EN/DE/IT`, `LANGUES` | `test-contrat.js` (exact key parity, all languages) |
| Release notes (fr + en only) | `v2/web/src/versions.ts` (`fr[]` / `en[]` per entry) | `test-contrat.js` (parity **note for note**) |
| Language setting | `config.json` (`langue: '' \| code`), owned by the main process | — |

**`fr.ts` is the source of truth.** Its `Cle` type is derived from its keys; every other
dictionary must cover exactly those keys. A missing or invented key stops `npm test`
(run it from the repository root).

## The rules that are not obvious from the code

- **The diagnostic log is always English**, whatever the UI language. It is the language
  of bug reports in an open project. Subjects too (`startup`, `update`, `watch`, `ui`…),
  and written levels are `info`/`warn`/`error`. Never translate `journal.*` lines.
- **Release notes exist in French and English only.** Other languages read the English
  ones (`changementsDe()` in `versions.ts`). Translating the changelog four ways at every
  release is exactly where discipline would die — don't start.
- **Language names translate never.** «Français», «English», «Deutsch», «Italiano» each
  written in their own language, in the registry (`LANGUES[code].nom`) — that is how you
  find yours in an interface you cannot read.
- **Data is not UI.** Camera names, watch names the user saved, color words returned by
  the controller, file names: they are data and keep their stored form. The default
  watches are seeded **once**, in the language of first launch, then belong to the user.
- **The browser demo mirrors the main process.** `v2/web/src/lib/bridge.ts` simulates
  the connection test and the relay with the *same* `etape.*`/`relais.*` keys as
  `v2/desktop/i18n.js`. If you change a main-process message, change its demo twin — the
  demo is how those texts get verified without real cameras.
- **Dates, hours and decimals follow the language**: `localeDates()` and `nombre()` in
  the web `i18n`, `localeHeure()` in the desktop one. Never hardcode `'fr-CH'` or
  `.replace('.', ',')` in a screen.
- **Pushed messages keep their emission language.** A relay state already displayed
  stays as it was until the next event after a language switch. Known and accepted — do
  not "fix" it by re-translating stored strings.

## Add or change a UI string

1. Add the key to `fr.ts` (French text). Keys are flat, dotted, grouped by screen
   (`reglages.confort.son`), parameters written `{nom}`.
2. `npm test` now fails listing every dictionary missing the key. Add the translations.
3. In the screen, call `t('the.key')` — components subscribe with
   `const t = useLangue();` (or a bare `useLangue();` if they use the module-level `t`).
4. Main-process strings follow the same steps in `v2/desktop/i18n.js` (all four tables);
   `test-contrat.js` enforces parity there.

Never put a user-visible literal in a component or in the main process. The accent scan
used during the conversion was: any `é/è/à/…` outside comments is a suspect.

## Add a language

Budget: the translation itself (~310 web keys + ~100 desktop keys) plus **two registry
lines**. Nothing else, and the build refuses anything incomplete.

1. **Web**: copy `v2/web/src/i18n/en.ts` to `xx.ts`, rename the export, translate all
   values. The `Record<Cle, string>` type will hold you to completeness.
2. Register it in `v2/web/src/i18n/index.ts`:
   `xx: { dictionnaire: xx, locale: 'xx-XX', nom: 'NativeName' }` — the settings
   selector, the demo auto-detection and the date/number formats pick it up from there.
3. **Desktop**: add an `XX` table in `v2/desktop/i18n.js` (same keys as `FR` — the
   parity test lists what is missing) and one line in its `LANGUES` registry.
4. `npm test` from the root. Then check in the demo (`npm run web`, Settings → your
   language) — walk Live, Replay, Detections, Alerts, and run the fake connection test.
5. That's all. `langueEffective()` (Windows-language default), the IPC, the settings
   screen and the demo need **no** change: they read the registries.

Conventions inside a dictionary: sober and factual, no exclamation marks, informal
address (tu / du / tu) mirroring the French, and for German: **Swiss spelling — «ss»,
never «ß»** (the project lives in Switzerland, locale `de-CH`).

## What proves what

| Check | Proves |
|---|---|
| `tsc` (via `npm test`) | every web dictionary covers exactly the keys of `fr.ts` |
| `test-contrat.js` — dictionnaire du principal | every desktop table covers exactly the keys of `FR` |
| `test-contrat.js` — historique | every release note has its English twin, note for note |
| `test-veilles.js` | every watch subject has a readable label in every language |
| Browser demo (manual) | live switching, layouts with longer German strings, the connection-test texts |

Each of these guards was proven by re-injecting the defect it watches for (removing a
key, dropping a translated note) and watching it fail. If you touch a guard, do that
again — a guard that has never failed protects nothing.
